# 总体需求分析

## 一、项目概述

### 1.1 项目名称
实时竞拍大师 - 直播竞拍全栈系统

### 1.2 项目定位
面向直播电商场景的全栈竞拍系统，支持高并发实时竞拍。系统包含三大子系统：
- **微信小程序用户端**：面向C端消费者，提供商品浏览、实时竞拍、订单管理、AI智能出价辅助
- **商家Web管理端**：面向B端商家，提供商品管理、竞拍管理、订单管理、直播间监控、AI运营辅助、数据分析
- **后端API服务**：提供RESTful API + WebSocket实时通信，支撑两端业务逻辑

### 1.3 核心价值
- 将直播电商与竞拍模式结合，创造新型购物体验
- AI赋能全链路：从商品定价、描述生成到出价策略、直播话术
- 实时竞拍引擎：高并发出价、自动延时、WebSocket毫秒级推送
- 完整商业闭环：商品 → 竞拍 → 订单 → 物流 → 售后

### 4.2 认证机制
- **方案**：JWT双Token（access_token + refresh_token）
- **access_token**：短期有效（如2小时），用于API请求鉴权
- **refresh_token**：长期有效（如7天），用于刷新access_token
- **传输方式**：Authorization: Bearer {token}
- **刷新策略**：access_token过期时自动使用refresh_token刷新

### 4.3 统一响应格式
```json
{
  "success": true,
  "data": {},
  "message": "操作成功"
}
```

### 4.4 分页参数
- `page`: 页码（默认1）
- `pageSize`: 每页条数（默认10）
- 响应包含：`total`、`page`、`pageSize`、`data`

## 五、实时通信设计

### 5.1 WebSocket架构
- **协议**：Socket.IO
- **房间机制**：每个竞拍独立房间（`auction_{id}`），互不干扰
- **连接管理**：自动重连、心跳检测

### 5.2 事件定义

| 事件名 | 方向 | 触发场景 | 数据内容 |
|--------|------|----------|----------|
| join_auction | Client→Server | 进入直播间 | auctionId |
| leave_auction | Client→Server | 离开直播间 | auctionId |
| place_bid | Client→Server | 提交出价 | auctionId, amount |
| new_bid | Server→Client | 有人出价 | 出价信息、新价格 |
| price_update | Server→Client | 价格更新 | 当前价格、出价者 |
| time_extended | Server→Client | 竞拍延时 | 新结束时间、延时秒数 |
| auction_ended | Server→Client | 竞拍结束 | 最终价格、获胜者 |
| auction_won | Server→Client | 竞拍获胜 | 订单信息 |
| outbid | Server→Client | 被超越 | 新出价者、新价格 |

### 5.3 并发控制
- **乐观锁**：出价时使用Redis乐观锁，防止并发出价导致数据不一致
- **Redis排行榜**：使用Redis Sorted Set维护实时排行榜，毫秒级更新
- **消息优化**：WebSocket优化器批量发送、去重、节流

### 9.2 竞拍出价校验流程

```
用户提交出价
    │
    ▼
[1.基础校验] → 金额非空/正数/数字 → 失败: 返回错误
    │
    ▼
[2.状态校验] → 竞拍是否active → 失败: "竞拍未在进行中"
    │
    ▼
[3.最低出价校验] → 出价 ≥ 当前价+加价幅度 → 失败: "出价低于最低加价"
    │
    ▼
[4.封顶价校验] → 出价 ≤ 封顶价 → 失败: "出价超过封顶价"
    │
    ▼
[5.智能提示] → AI分析出价合理性 → 警告: "出价偏高，请注意风险"
    │
    ▼
出价成功 → Redis乐观锁写入 → WebSocket广播 → 排行榜更新
    │
    ▼
检查是否需要延时 → 结束前出价 → 自动延时10-30秒
```

### 9.3 订单状态流转

```
                    ┌──────────┐
                    │  pending  │ (待付款)
                    └─────┬────┘
                          │ 付款
                          ▼
                    ┌──────────┐
              ┌─────│   paid    │ (已付款) ─────┐
              │     └─────┬────┘                │
              │           │ 发货                 │ 申请退款
              │           ▼                     │
              │     ┌──────────┐          ┌──────────┐
              │     │  shipped  │          │ refunding │ (退款中)
              │     └──────────┘          └─────┬────┘
              │                                 │
              │                    ┌────────────┼────────────┐
              │                    │ 同意退款    │            │ 拒绝退款

              │              ┌──────────┐       │      ┌──────────┐
              │              │ refunded  │       │      │   paid    │

              │                                 │
              │  取消订单(待付款时)                │

        ┌──────────┐                            │
        │ cancelled │ <─────────────────────────┘
        └──────────┘       取消订单(退款被拒后)
```

## 十、通知体系设计

### 10.1 通知类型

| 通知类型 | 标识 | 接收方 | 触发场景 |
|----------|------|--------|----------|
| 新订单 | new_order | 商家 | 竞拍结束生成订单 |

## 十三、风险与挑战

### 13.1 技术风险

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| 高并发出价 | 数据不一致/超卖 | Redis乐观锁 + 原子操作 |
| WebSocket断连 | 实时数据丢失 | 自动重连 + 心跳检测 |
| AI服务不可用 | AI功能失效 | 降级策略 + 缓存 + 模板兜底 |
| 数据库慢查询 | 响应变慢 | 索引优化 + 慢查询监控 + 缓存 |
| 内存泄漏 | 服务崩溃 | 内存守护 + 堆监控 + 自动GC |

### 13.2 业务风险

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| 恶意出价/刷单 | 竞拍不公平 | 用户限流 + 出价校验 + 审计日志 |
| 退款纠纷 | 商家损失 | 退款审核流程 + 拒绝原因记录 |
| 价格操纵 | 用户体验差 | AI风险提示 + 异常出价检测 |
| AI幻觉/错误建议 | 误导用户 | 置信度展示 + 风险评估 + 免责声明 |
